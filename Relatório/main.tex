\chapter*{Glossário}
\begin{description}
    \item[Middleware] Componente lógico intermédio (como filtros de segurança) que interceta pedidos HTTP para realizar validações antes de chegarem aos controladores.
    \item[Pessimistic Locking] Estratégia de controlo de concorrência que bloqueia registos na base de dados durante uma transação para evitar condições de corrida.
    \item[Stateless] Estilo de arquitetura onde o servidor não mantém qualquer estado de sessão do utilizador, sendo cada pedido autossuficiente para validação.
    \item[Thread] Linha de execução independente dentro de um processo, permitindo realizar tarefas de forma concorrente no backend.
\end{description}


\chapter{Introdução}

\section{Enquadramento}
No âmbito da unidade curricular de Sistemas Distribuídos, foi proposto o desenvolvimento de uma aplicação web completa para uma loja online. O tema escolhido pelo grupo foi uma \textbf{Loja de Eletrodomésticos}, implementada recorrendo à framework Spring para o backend e React para o frontend.

Este projeto foca-se na criação de serviços RESTful, persistência de dados e, crucialmente, na segurança e gestão de sessões de utilizadores num ambiente distribuído. Todo o código-fonte pode ser consultado no repositório GitHub do projeto através do endereço \url{https://github.com/Vascorc/Loja_Eletrodomesticos}.

\section{Objetivos}
O objetivo principal é desenvolver uma plataforma que permita a gestão de um catálogo de produtos, a realização de compras por clientes registados e a administração de stocks.

Os objetivos específicos incluem:
\begin{enumerate}
    \item Implementação de uma API RESTful utilizando Spring Boot.
    \item Persistência de dados num SGBD relacional (PostgreSQL).
    \item Implementação de um sistema de segurança robusto com autenticação JWT (JSON Web Tokens).
    \item Gestão de sessões stateless para garantir escalabilidade.
    \item Integração do Frontend com o Backend através de serviços assíncronos.
    \item Desenvolvimento de lógica distribuída para processamento de vendas, faturas e controlo de stocks concorrente.
\end{enumerate}

\chapter{Tecnologias e Ferramentas Utilizadas}

\section{Spring Framework e Spring Security}
O backend foi desenvolvido com Spring Boot, utilizando o ecossistema Spring Security para gerir a autenticação e autorização. Esta escolha permitiu uma integração simplificada de mecanismos de segurança avançados.

\section{JSON Web Tokens (JWT)}
Para a gestão de sessões, optou-se por JWT. Esta tecnologia permite que o servidor não necessite de guardar estado (stateless), o que é ideal para sistemas distribuídos, pois o token enviado pelo cliente contém toda a informação necessária para a sua identificação, permitindo que a API escale sem necessidade de partilhar sessões entre instâncias.

\section{PostgreSQL}
A persistência de dados é assegurada pelo PostgreSQL, um SGBD relacional robusto que garante a integridade dos dados de utilizadores, produtos e vendas.

\section{React e Vite}
O frontend foi construído utilizando React, uma biblioteca JavaScript para a criação de interfaces de utilizador dinâmicas.

\chapter{Modelo de Dados}

O modelo de dados da aplicação foi projetado para suportar todas as operações de e-commerce, o controlo transacional de inventário e o sistema de segurança stateless. A persistência é gerida através da especificação JPA (Java Persistence API) com o Hibernate como fornecedor ORM subjacente, mapeando classes Java diretamente para tabelas na base de dados relacional PostgreSQL.

\section{Descrição das Entidades}
O modelo é constituído por 6 entidades principais, cujos propósitos e estruturas são descritos detalhadamente a seguir:
\begin{enumerate}
    \item \textbf{Utilizador (\texttt{utilizador})}: Armazena os dados cadastrais e as credenciais de segurança de clientes e administradores.
    \begin{itemize}
        \item \texttt{id} (SERIAL PRIMARY KEY): Identificador único numérico gerado automaticamente.
        \item \texttt{nome} (VARCHAR): Nome completo do utilizador.
        \item \texttt{email} (VARCHAR, UNIQUE): Endereço de correio eletrónico, usado como credencial única de login.
        \item \texttt{password} (VARCHAR): Hash de palavra-passe encriptada usando BCrypt.
        \item \texttt{perfil} (VARCHAR): Nível de privilégio do utilizador (\texttt{CLIENTE} ou \texttt{ADMIN}).
    \end{itemize}

    \item \textbf{Categoria (\texttt{categoria})}: Modela as categorias ou famílias de eletrodomésticos (e.g., Frigoríficos, Fogões).
    \begin{itemize}
        \item \texttt{id} (SERIAL PRIMARY KEY): Identificador único da categoria.
        \item \texttt{nome} (VARCHAR, UNIQUE): Designação única da categoria.
        \item \texttt{descricao} (TEXT): Detalhes adicionais sobre a categoria.
    \end{itemize}

    \item \textbf{Produto (\texttt{produto})}: Contém as especificações técnicas, preço, imagem e estado de stock de cada eletrodoméstico à venda.
    \begin{itemize}
        \item \texttt{id} (SERIAL PRIMARY KEY): Identificador único numérico do artigo.
        \item \texttt{nome} (VARCHAR): Nome comercial do artigo.
        \item \texttt{marca} (VARCHAR), \texttt{modelo} (VARCHAR): Marca e modelo do fabricante.
        \item \texttt{preco} (DECIMAL): Preço unitário em Euros.
        \item \texttt{stock} (INTEGER): Quantidade física disponível em armazém.
        \item \texttt{eficiencia\_energetica} (VARCHAR): Classificação de consumo energético (e.g., A, B).
        \item \texttt{imagem\_url} (VARCHAR): Link ou URL da imagem do produto.
        \item \texttt{categoria\_id} (INTEGER REFERENCES \texttt{categoria}): Chave estrangeira que classifica o produto.
    \end{itemize}

    \item \textbf{Venda (\texttt{venda})}: Regista a transação global efetuada por um cliente, funcionando como cabeçalho de faturação.
    \begin{itemize}
        \item \texttt{id} (SERIAL PRIMARY KEY): Número sequencial da venda/fatura única.
        \item \texttt{data\_venda} (TIMESTAMP): Data e hora exatas da conclusão da compra.
        \item \texttt{valor\_total} (DECIMAL): Custo final acumulado dos produtos adquiridos.
        \item \texttt{utilizador\_id} (INTEGER REFERENCES \texttt{utilizador}): Chave estrangeira que associa a compra a um cliente registado.
        \item \texttt{metodo\_pagamento} (VARCHAR): Método escolhido (ex: PayPal, Cartão).
        \item \texttt{morada}, \texttt{cidade}, \texttt{codigo\_postal}, \texttt{telefone} (VARCHAR): Dados de faturação e entrega fornecidos no checkout.
    \end{itemize}

    \item \textbf{Item de Venda (\texttt{item\_venda})}: Armazena os detalhes dos produtos contidos em cada venda.
    \begin{itemize}
        \item \texttt{id} (SERIAL PRIMARY KEY): Identificador único da linha de faturação.
        \item \texttt{venda\_id} (INTEGER REFERENCES \texttt{venda}): Associação à fatura global.
        \item \texttt{produto\_id} (INTEGER REFERENCES \texttt{produto}): Produto adquirido.
        \item \texttt{quantidade} (INTEGER): Unidades compradas.
        \item \texttt{preco\_unitario} (DECIMAL): Preço unitário praticado na transação (estático, salvaguardando alterações de preço posteriores).
    \end{itemize}

    \item \textbf{Reserva (\texttt{reservas})}: Mecanismo de concorrência distribuída que impede o over-selling na base de dados distribuída, cativando temporariamente os artigos por 5 minutos no carrinho do utilizador.
    \begin{itemize}
        \item \texttt{id} (SERIAL PRIMARY KEY): Identificador único da reserva.
        \item \texttt{produto\_id} (INTEGER REFERENCES \texttt{produto}): Produto alocado.
        \item \texttt{utilizador\_id} (INTEGER REFERENCES \texttt{utilizador}): Utilizador que efetuou a reserva.
        \item \texttt{quantidade} (INTEGER): Unidades reservadas.
        \item \texttt{data\_expiracao} (TIMESTAMP): Data limite para fecho da compra antes de o stock retornar ao catálogo geral.
    \end{itemize}
\end{enumerate}

\chapter{Arquitetura e Implementação do Sistema}

\section{Arquitetura de Segurança}
A segurança da aplicação foi desenhada de raiz para proteger de forma robusta e consistente os dados dos utilizadores, bem como controlar o acesso a recursos sensíveis. A implementação garante a integridade de todas as rotas do frontend e endpoints REST do backend, organizando as tarefas de segurança nos seguintes eixos fundamentais:

\subsection{Estrutura de Utilizadores e Controlo de Perfis}
O modelo de utilizadores baseia-se na classe \texttt{Utilizador}, persistida na tabela homónima da base de dados. Cada utilizador é associado a um determinado perfil de acesso através do campo \texttt{perfil}, cujos valores possíveis são:
\begin{itemize}
    \item \textbf{CLIENTE}: Utilizador comum da loja, com permissão para navegar pelo catálogo, reservar produtos temporariamente no carrinho e concluir compras.
    \item \textbf{ADMIN}: Utilizador com privilégios administrativos completos sobre a gestão de produtos, stock de inventário, categorias, e visualização de faturas e histórico global de vendas.
\end{itemize}
Na integração com o Spring Security, o perfil é mapeado para um conjunto de autoridades concedidas (\texttt{GrantedAuthority}), prefixado com \texttt{ROLE\_} (e.g., \texttt{ROLE\_CLIENTE} e \texttt{ROLE\_ADMIN}), viabilizando o controlo de acesso baseado em perfis tanto a nível global como a nível de controladores específicos.

\subsection{Registo de Clientes e Fluxo de Login/Logout}
\begin{itemize}
    \item \textbf{Registo de Clientes}: Disponibilizado através do endpoint público \texttt{/api/auth/signup}. A password fornecida pelo utilizador é encriptada utilizando o algoritmo unidirecional robusto \textbf{BCrypt} antes de ser persistida. Isto garante que as passwords nunca são guardadas em texto limpo.
    \item \textbf{Login}: Efetuado via \texttt{/api/auth/signin}. O \texttt{AuthenticationManager} valida o email e a password introduzidos. Caso as credenciais coincidam com os registos cifrados da BD, o servidor emite um token de autenticação assinado e configurado.
    \item \textbf{Logout}: Gerido de forma \textit{stateless} no frontend. Ao acionar o botão de logout, a aplicação cliente elimina o token JWT armazenado no \texttt{localStorage} do browser e reencaminha o utilizador para a página de login, limpando qualquer estado em cache.
\end{itemize}

\subsection{Gestão de Sessões Stateless com JWT e Expiração}
Para permitir a escalabilidade distribuída do sistema, optou-se por uma gestão de sessões \textit{stateless}. O servidor não armazena nenhuma sessão em memória; toda a informação necessária para identificar e conceder permissões ao utilizador é encapsulada num token seguro do tipo \textbf{JSON Web Token (JWT)}.
Cada token possui um tempo de expiração estrito (configurado por omissão para 24 horas). Uma vez expirado o token, a sua assinatura deixa de ser válida e o utilizador é forçado a reautenticar-se.

\subsection{Filtro de Segurança e Middleware de Autenticação}
Foi desenvolvido um middleware específico designado \texttt{AuthTokenFilter} que estende a classe \texttt{OncePerRequestFilter} do Spring Security. Este filtro é executado a cada pedido HTTP enviado para a API:
\begin{enumerate}
    \item Extrai o cabeçalho \textit{Authorization} do pedido e analisa o prefixo \textit{Bearer}.
    \item Utiliza a classe utilitária \texttt{JwtUtils} para validar a assinatura, integridade e expiração do token.
    \item Recupera a identidade do utilizador (email) a partir do token.
    \item Carrega os dados correspondentes através de \texttt{UserDetailsServiceImpl} e estabelece o objeto \texttt{UsernamePasswordAuthenticationToken} no contexto global de segurança do Spring (\texttt{SecurityContextHolder}).
\end{enumerate}

\subsection{Proteção de Rotas e Controlo de Acesso End-to-End}
Para assegurar a máxima proteção, as verificações foram duplicadas em ambas as camadas da aplicação:
\begin{itemize}
    \item \textbf{Frontend (Proteção de Rotas em React):}
    Criou-se o componente de ordem superior \texttt{ProtectedRoute}. Este componente encapsula rotas privadas na aplicação. Se o utilizador não possuir um token ativo no \texttt{localStorage}, é reencaminhado para \texttt{/login}. 
    Para as rotas dedicadas à administração (como \texttt{/admin/produtos} e \texttt{/admin/vendas}), o componente valida se o perfil do utilizador é estritamente \texttt{ADMIN}. Utilizadores sem o perfil devido são bloqueados e redirecionados para a raiz \texttt{/}.
    
    \item \textbf{Backend (Segurança Geral e Endpoints da API):}
    A configuração da cadeia de filtros em \texttt{WebSecurityConfig} desativa a proteção CSRF (visto que as comunicações usam tokens em vez de cookies) e autoriza de forma pública apenas os endpoints estritamente necessários (registo, login e operações de consulta). Adicionalmente, implementou-se segurança ao nível do método recorrendo a anotações \texttt{@PreAuthorize}:
\end{itemize}

\begin{lstlisting}[caption={Configuração do SecurityFilterChain no Backend (WebSecurityConfig)}]
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http.cors(Customizer.withDefaults())
        .csrf(csrf -> csrf.disable())
        .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(auth -> auth
            .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()
            .requestMatchers("/api/auth/**").permitAll()
            .requestMatchers("/api/test/**").permitAll()
            .requestMatchers("/api/produtos/public/**").permitAll()
            .requestMatchers(HttpMethod.GET, "/api/categorias/**").permitAll()
            .anyRequest().authenticated()
        );
    http.authenticationProvider(authenticationProvider());
    http.addFilterBefore(authenticationJwtTokenFilter(), UsernamePasswordAuthenticationFilter.class);
    return http.build();
}
\end{lstlisting}

Para garantir que apenas administradores possam gerir produtos e categorias, aplicámos a restrição baseada em perfis diretamente nos controladores do backend:
\begin{lstlisting}[caption={Anotação PreAuthorize no ProdutoController}]
@PostMapping
@PreAuthorize("hasRole('ADMIN')")
public ResponseEntity<ProdutoDTO> criar(@RequestBody ProdutoDTO dto) { ... }

@PutMapping("/{id}")
@PreAuthorize("hasRole('ADMIN')")
public ResponseEntity<ProdutoDTO> atualizar(@PathVariable Long id, @RequestBody ProdutoDTO dto) { ... }
\end{lstlisting}

\subsection{Validação de Dados e Proteção de Inputs}
Para robustecer a segurança contra dados inválidos e vulnerabilidades comuns de segurança (como SQL Injections):
\begin{itemize}
    \item O backend utiliza mapeamento JPA e repositórios Spring Data com consultas parametrizadas, neutralizando de forma inerente ataques de injeção de código SQL.
    \item A nível de serviços e controladores, todas as operações de escrita validam o estado das variáveis de entrada, garantindo a integridade dos dados na base de dados relacional.
\end{itemize}

\section{Integração Frontend-Backend}
A comunicação entre as duas camadas é feita através de serviços assíncronos no frontend. Criou-se um \texttt{AuthService} em JavaScript que utiliza a API \textit{fetch} para consumir os endpoints REST do backend. O token recebido é armazenado no \texttt{localStorage} para persistência da sessão no browser.

\section{Gestão de Catálogo e Vendas}
A gestão do catálogo e o processamento de vendas formam o verdadeiro coração da aplicação. Na prática, o sistema divide-se em duas grandes dinâmicas que trabalham em conjunto: a manutenção contínua dos produtos e todo o ciclo de vida que acompanha uma venda.

\subsection{Gestão de Catálogo}

Para dar vida ao catálogo, assentamos a lógica nos serviços \texttt{ProdutoService} e \texttt{CategoriaService}, que garantem o ciclo completo de operações CRUD. O utilizador pode explorar os produtos de forma simples, seja navegando pela listagem global, aplicando filtros por categorias ou fazendo pesquisas diretas pelo nome. 

Há também uma funcionalidade inteligente de destaques: o sistema cruza os dados atuais com o histórico de vendas para calcular e expor automaticamente os 5 produtos mais populares do momento. 

Para proteger a arquitetura do sistema, a comunicação entre o \textit{backend} e o \textit{frontend} nunca expõe o modelo de domínio interno de forma direta. Em vez disso, utilizamos DTOs (\textit{Data Transfer Objects}), como o \texttt{ProdutoDTO}, que servem como uma camada segura de isolamento.

\subsection{Gestão de Vendas (Carrinho e Checkout)}

A experiência de compra começa quando o utilizador adiciona um artigo ao carrinho, disparando de imediato um mecanismo de reserva temporária de stock. Quando decide avançar para o \textit{checkout}, o sistema recolhe os dados de envio e pagamento através do \texttt{CheckoutRequestDTO} e submete-os para processamento.

É neste momento que o \textit{backend} assume o controlo através de um fluxo estruturado:
\begin{itemize}
    \item Percorre detalhadamente cada um dos itens guardados no carrinho;
    \item Calcula o valor total finalizado do pedido;
    \item Gera e persiste as respetivas entidades de \texttt{Venda} e \texttt{ItemVenda}.
\end{itemize}

Assim que a transação é concluída com sucesso, a venda fica imediatamente vinculada ao perfil do \texttt{Utilizador} autenticado. O registo passa a estar disponível para consulta no seu histórico pessoal de compras e na área de faturação.

\section{Lógica de Negócio e Serviços}
A arquitetura do backend foi desenhado seguindo um modelo de camadas focado no domínio. Toda a lógica de negócio fica estritamente isolada na camada de serviços --- identificados pela anotação \code{@Service} do Spring Boot. Esta abordagem garante uma separação clara de responsabilidades, evitando que as regras de processamento se misturem com os controladores REST ou com a persistência de dados nos repositórios.

A dinâmica de compras e vendas assenta em três pilares principais:

\subsection*{ProdutoService} 
Centraliza toda a gestão e validação dos produtos. É responsável por verificar a existência de categorias associadas durante os processos de criação ou atualização, garantindo também uma conversão precisa e segura entre as entidades da base de dados e os DTOs.

\subsection*{VendaService} 
Orquestra o fluxo crítico de finalização de compra. O método de \textit{checkout} opera sob um contexto transacional (\code{@Transactional}), validando a identidade do utilizador antes de construir a entidade de venda. A partir daí, percorre os itens do pedido para delegar a verificação de disponibilidade física e a respetiva retenção de stock. Adicionalmente, este componente gere o histórico de compras dos clientes --- aplicando os filtros de segurança necessários --- e disponibiliza uma visão consolidada das vendas para o perfil de administrador.

\subsection*{ReservaService} 
Controla o ciclo de vida temporal do carrinho de compras. Assim que um produto é reservado, o sistema deduz temporariamente essa quantidade do stock por um período de 5 minutos. Para melhorar a experiência do utilizador e evitar frustrações, o sistema renova automaticamente o prazo de expiração de todas as reservas ativas daquele perfil sempre que um novo item é adicionado ao carrinho.


\section{Processamento de Vendas e Stocks}
Para evitar que múltiplos utilizadores comprem o mesmo produto em simultâneo, o sistema utiliza uma estratégia dupla de sincronização: bloqueios imediatos na base de dados e um circuito de reservas temporárias.

\paragraph{Isolamento de Concorrência e Abordagem Comparativa (JVM vs. Base de Dados):}
Para justificar o desenho do sistema no âmbito de Sistemas Distribuídos, analisou-se detalhadamente a estratégia de exclusão mútua no acesso concorrente ao stock, avaliando duas hipóteses principais:
\begin{enumerate}
    \item \textbf{Sincronização em Memória (\texttt{synchronized} na JVM):} A utilização de monitores e blocos declarados como \texttt{synchronized} em Java é uma solução clássica para exclusão mútua ao nível de \textit{threads} a correr localmente numa única máquina virtual. No entanto, esta hipótese apresenta duas limitações graves para o projeto:
    \begin{itemize}
        \item \textit{Limitação de Distribuição:} Num sistema distribuído, onde o backend pode ser escalado horizontalmente (múltiplas instâncias físicas da API a correr em paralelo atrás de um \textit{Load Balancer}), cada JVM terá a sua própria memória \textit{heap} isolada. Como os trincos locais não se propagam pela rede, dois servidores distintos permitiriam vendas concorrentes incorretas, gerando rutura e inconsistência de stock (*over-selling*).
        \item \textit{Desconexão com a Base de Dados:} Uma vez que o stock não reside no Heap do Java mas sim no PostgreSQL, sincronizar apenas a execução na JVM não impede que duas transações assíncronas concorrentes leiam dados obsoletos da base de dados se as transações não forem bloqueadas a nível relacional.
    \end{itemize}

    \item \textbf{Bloqueio Pessimista na Base de Dados (Abordagem Adotada):} O sistema protege o acesso ao inventário através de bloqueio pessimista (\textit{Pessimistic Locking}), recorrendo à anotação \texttt{@Lock(LockModeType.PESSIMISTIC\_WRITE)} no método \texttt{findByIdWithPessimisticLock} do repositório. Esta instrução gera a cláusula SQL nativa \texttt{SELECT ... FOR UPDATE} na base de dados, sendo a solução ideal devido aos seguintes fatores:
    \begin{itemize}
        \item \textit{Sincronização Distribuída Inerente:} Como todas as réplicas ou instâncias da API de backend partilham a mesma base de dados PostgreSQL, o SGBD funciona como a única fonte de verdade e o coordenador distribuído de concorrência. O bloqueio é aplicado à linha física da tabela \texttt{produto}, forçando qualquer outra instância a aguardar em fila.
        \item \textit{Consistência Forte:} Elimina o risco de anomalias de escrita concorrente (*lost updates*), pois a linha fica retida para escrita e leitura protegida até que a transação inicial efetue o respetivo \textit{commit} ou \textit{rollback}, mantendo a integridade absoluta do stock de inventário.
    \end{itemize}
\end{enumerate}

\paragraph{Fluxo de Reserva Dinâmica:}
Para mitigar a frustração de ruturas de stock a meio do pagamento, o processo foi estruturado em três etapas:
\begin{itemize}
    \item \textbf{Adição ao carrinho:} Assim que o item entra no carrinho, o stock é deduzido e alocado provisoriamente na entidade \texttt{Reserva}.
    \item \textbf{Finalização da compra:} No momento do checkout, o \texttt{VendaService} liquida a reserva ativa sem reprocessar o stock do produto.
    \item \textbf{Verificação de segurança:} Falhas ou omissões na reserva forçam a validação direta no inventário livre, disparando uma \textit{Runtime Exception} caso o saldo seja insuficiente.
\end{itemize}

\paragraph{Libertação Automática de Recursos:}
Para que o stock não fique retido indefinidamente em carrinhos abandonados, o componente \texttt{ReservaCleanupTask} executa uma rotina cíclica em background. Esta tarefa identifica reservas expiradas, devolve os artigos ao inventário disponível do \texttt{Produto} e elimina o registo temporário, assegurando a rotação contínua do catálogo.


\chapter{Testes e Validação do Sistema}
Neste capítulo, é apresentada a validação prática e o plano de testes executado para comprovar a correta implementação e a robustez dos requisitos funcionais e técnicos definidos para o sistema. O processo de verificação cobriu desde o comportamento da interface de utilizador (frontend) até às regras de negócio, controlo transacional concorrente e políticas de segurança impostas pelo Spring Security (backend). As secções seguintes detalham os cenários simulados, a recolha de evidências de funcionamento e a resposta da plataforma face a acessos válidos e tentativas de intrusão.

\section{Segurança e Autenticação}
Para testar a fiabilidade do sistema de segurança concebido, foram conduzidos testes de validação focados em cenários de acesso não autorizado:
\begin{enumerate}
    \item \textbf{Verificação de Sessão Ativa:} Ao aceder ao dashboard ou ao catálogo de produtos sem um token de autenticação válido armazenado, o componente \texttt{ProtectedRoute} do React bloqueia imediatamente o carregamento do conteúdo e redireciona o utilizador para a página de \texttt{/login}.
    \item \textbf{Fluxo de Registo e Login com Sucesso:} Testou-se a criação de um utilizador comum e a autenticação do mesmo. O token JWT foi emitido com sucesso pelo servidor e carregado no cabeçalho HTTP de todos os pedidos assíncronos seguintes.
    \item \textbf{Validação de Acesso Restrito no Frontend:} Efetuou-se login com um utilizador comum (perfil \texttt{CLIENTE}). Ao tentar forçar o URL de administração no browser (\texttt{http://localhost:5173/admin/produtos}), o componente de segurança barrou o acesso e reencaminhou o utilizador de volta para o dashboard principal.
    \item \textbf{Teste de Bloqueio de Endpoints no Backend:} Através da simulação direta de pedidos REST HTTP para os endpoints reservados (e.g., pedidos POST para \texttt{/api/produtos} ou \texttt{/api/categorias}) utilizando ferramentas como Postman e enviando um token de utilizador com perfil \texttt{CLIENTE}, a API do Spring Boot respondeu com o estado de erro \textbf{403 Forbidden}, validando com absoluto rigor a eficácia das anotações \texttt{@PreAuthorize("hasRole('ADMIN')")}.
\end{enumerate}

\section{Gestão de Produtos}
Para validar as funcionalidades de administração do catálogo, foi testada a página de \textbf{Gestão de Produtos} (acessível exclusivamente a utilizadores com o perfil \texttt{ADMIN}). As operações CRUD (Create, Read, Update, Delete) foram avaliadas da seguinte forma:
\begin{enumerate}
    \item \textbf{Leitura (Read):} Verificou-se que a tabela principal carrega com sucesso todos os produtos disponíveis no sistema, exibindo de forma clara a imagem, nome, categoria, preço, stock atual e eficiência energética. Adicionalmente, testou-se o feedback visual para níveis críticos de stock (destaques em estilos condicionados para rutura de stock ou stock baixo).
    \item \textbf{Criação (Create):} Através da ação ``Novo Produto'', foi aberto um formulário modal. Procedeu-se ao preenchimento de todos os dados do novo eletrodoméstico (incluindo o URL da imagem, seleção da categoria e nível de eficiência). Ao submeter, o novo registo foi imediatamente persistido na base de dados e a tabela foi atualizada de forma imediata.
    \item \textbf{Atualização (Update):} Utilizando a opção ``Editar'' num produto existente, o formulário modal foi pré-preenchido com os dados atuais do eletrodoméstico. Após a modificação do preço e da quantidade em stock, as alterações foram gravadas com sucesso e validadas na listagem da administração.
    \item \textbf{Eliminação (Delete):} Foi testada a operação de remoção de um produto clicando no botão ``Eliminar''. O sistema apresentou um alerta de confirmação no browser, prevenindo eliminações acidentais. Após a confirmação, o produto foi permanentemente removido e a lista limpa da interface.
\end{enumerate}
Todos os pedidos efetuados durante a validação das funcionalidades incluíram o \textit{JSON Web Token} no formato Bearer associado a um administrador. Isto assegurou que as validações de autorização, asseguradas pelo \texttt{WebSecurityConfig} no lado do servidor, fossem efetuadas em harmonia com as proteções no frontend.
